# Fuzzing

Two targets, both first-class: the archive parser and the request parser. Both
need a nightly toolchain and `cargo-fuzz`.

```console
$ make fuzz                 # both targets, 60s each, from the committed seeds
$ make fuzz FUZZ_TIME=600   # longer
$ make fuzz-seed            # minimise the corpus and fold it into the seeds
```

| Target | Input | Reaches |
|---|---|---|
| `archive` | a whole `.zim` file | `zimfmt` header, MIME table, pointer lists, dirents, clusters, decompression |
| `request` | raw socket bytes | `api` request line, headers, percent-decoding, `Range`, routing |

## The corpus is kept

`fuzz/seeds/` is committed and is where every run starts. `fuzz/corpus/` is the
working set and is not committed.

A corpus discarded at the end of every run only ever re-finds what the seeds
already reach. So the nightly job restores the previous night's corpus from the
Actions cache, fuzzes for 30 minutes a target, minimises with `cargo fuzz
cmin`, and saves it under a fresh key; `restore-keys` picks up the most recent
one because a cache entry cannot be overwritten. It also uploads the corpus as
an artifact, since the cache expires and the artifact is what a human can
download.

To fold what a nightly run found into the seeds, download its
`fuzz-corpus-<target>` artifact into `fuzz/corpus/<target>/`, run `make
fuzz-seed`, and commit `fuzz/seeds/`. Pull-request runs start from the seeds,
so this is how nightly coverage reaches them.

## Seeds

`fuzz/seeds/archive/` is generated by `zim-craft` (`crates/testutil`), so it is
regenerable rather than a pile of binaries nobody can explain. `xz-crash.zim`
pins D11: a crafted xz footer that panics `lzma-rs`, which `zimfmt` contains.

A crash reproduces with:

```console
$ cd fuzz && cargo +nightly fuzz run archive artifacts/archive/crash-<hash>
```
